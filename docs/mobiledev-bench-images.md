# MobileDev-Bench Android instance images: how they are built and run

Date: 2026-10-28. Source: `MobileDev-Bench/mobiledev-bench` @ `main` read via `gh api` (no clone, no Docker),
plus the upstream `mingchen/docker-android-build-box` @ tag `1.29.0` and anonymous reads of the
`ghcr.io` registry v2 API. Paths below are relative to the mobiledev-bench repo unless noted.
Every quoted line is verbatim; items are marked **found** (with path:line) or **not found**.

## 1. Build chain for Android (Kotlin/Java) tasks

**found** There are no Dockerfile templates on disk; `image.py` is abstract (`def dockerfile(self) -> str:` /
`raise NotImplementedError`, `mobiledev_bench/harness/image.py:120-121`). Each repo module defines two
classes, `<Repo>ImageBase` (tag `base`) and `<Repo>ImageDefault` (tag `pr-N`), whose `dockerfile()` returns
the text; the harness writes it with `f.write(image.dockerfile())` (`mobiledev_bench/harness/run_evaluation.py:615`)
and the helper files with `f.write(file.content)` (`run_evaluation.py:621`), then calls `docker_util.build`.
All 12 Kotlin modules and the one Java module (`repos/java/antennapod/antennapod.py`) are near-identical
copies of `repos/kotlin/tuskyapp/tusky.py`; citations use tusky.py and note deviations.

**Base image (found)**: `return "mingc/android-build-box:1.29.0"` — `mobiledev_bench/harness/repos/kotlin/tuskyapp/tusky.py:24`
(same line 24 in every kotlin/* and java/antennapod module).

**Per-repo "base" Dockerfile (found)**, generated by `TuskyImageBase.dockerfile()` (`tusky.py:82-116`):

```
FROM mingc/android-build-box:1.29.0          # tusky.py:102
USER root                                     # tusky.py:103
{global_env}                                  # ENV lines only if --global_env given (image.py:59-69)
WORKDIR /home/                                # tusky.py:106
ENV DEBIAN_FRONTEND=noninteractive            # tusky.py:107
ENV TZ=Etc/UTC                                # tusky.py:108
RUN git clone https://github.com/{org}/{repo}.git /home/{repo}   # tusky.py:88 (need_clone=True, the default: run_evaluation.py:113-117)
#   else: COPY {repo} /home/{repo}            # tusky.py:90
COPY detect_jdk.sh /tmp/detect_jdk.sh         # tusky.py:94  (AntennaPod copies to /home/detect_jdk.sh, antennapod.py:108)
RUN chmod +x /tmp/detect_jdk.sh && /tmp/detect_jdk.sh /home/{repo} {base.sha} > /opt/jenv/version && ... java -version   # tusky.py:95-99
{clear_env}                                   # ENV K="" for each --global_env key (image.py:77-87)
```

Caveat (found): the `base` image is shared per repo (`return "base"`, `tusky.py:27`; images compare by full
name, `image.py:43-49`; an existing image is skipped, `run_evaluation.py:599`) but its Dockerfile embeds
one PR's `{self.pr.base.sha}` (`tusky.py:96`). The JDK written to `/opt/jenv/version` is therefore detected
from whichever PR's base commit built the `base` image first, not necessarily the PR you are evaluating.

**Per-PR instance Dockerfile (found)**, generated by `TuskyImageDefault.dockerfile()` (`tusky.py:331-393`):

```
FROM mobiledevbench/{org}_mb_{repo}:base      # tusky.py:379 (f"FROM {name}:{tag}")
{global_env}
{proxy_setup}                                  # only if --global_env has http(s)_proxy (tusky.py:344-372)
COPY fix.patch /home/                          # loop: copy_commands += f"COPY {file.name} /home/\n" (tusky.py:337-338)
COPY test.patch /home/
COPY check_git_changes.sh /home/
COPY prepare.sh /home/
COPY run.sh /home/
COPY test-run.sh /home/
COPY fix-run.sh /home/
RUN bash /home/prepare.sh                      # tusky.py:340
{proxy_cleanup}
{clear_env}
```

WordPress adds `gradle.properties` to the COPY list (`repos/kotlin/wordpress_mobile/wordpress_android.py:174-176`).
The published image's layer history (ghcr config blob for `tuskyapp_mb_tusky:pr-2713`) matches this text
exactly: `git clone https://github.com/tuskyapp/Tusky.git /home/Tusky`, the detect_jdk RUN with sha
`271514f2...`, seven `COPY ... in /home/`, then `bash /home/prepare.sh`.

**WORKDIR / checkout path (found)**: `WORKDIR /home/` (`tusky.py:106`); the instance Dockerfile sets no WORKDIR,
so the image's WorkingDir is `/home` (confirmed in the ghcr config blob). The repository is at
`/home/{pr.repo}` (`tusky.py:88`, `cd /home/{pr.repo}` at `tusky.py:180,210,236,279`). Case is preserved
(`/home/Tusky`, `/home/AntennaPod`, `/home/WordPress-Android`, `/home/thunderbird-android`) even though the
image name is lowercased (`.lower()`, `image.py:100`).

**Checkout state (found)**: `prepare.sh`, run at image build, does `git reset --hard` (`tusky.py:181`),
`bash /home/check_git_changes.sh` (182), `git checkout {pr.base.sha}` (183), check again (184). So the
instance image is a detached HEAD at the PR base commit with the test patch NOT applied: `test-run.sh`
applies `/home/test.patch` at run time (`tusky.py:240`) and `fix-run.sh` applies test then fix (283, 296).
`check_git_changes.sh` exits 1 on `git status --porcelain` output (`tusky.py:164-166`), so the build fails
on a dirty tree. Note that `prepare.sh` also runs the full base test suite at build time (section 3).

## 2. git, python3, JDKs

**.git present (found)**: the repo is a real `git clone` (`tusky.py:88`); `check_git_changes.sh` relies on
`git rev-parse --is-inside-work-tree` (`tusky.py:159`). **Remote (found)**: nothing in the harness removes
`origin`; only the *inference* runner strips it at container start (`git remote remove origin || true`,
`mobiledev_bench/inference/backends/mini_swe_agent/runner.py:67`) and its docstring says it
"Deliberately does NOT `rm -rf .git`" (`runner.py:57`). Evaluation containers keep `origin`.

**python3 (found, version not established)**: the harness installs nothing but expects it:
`bash -c 'python3 /home/apply_begin_patch.py` (`run_evaluation.py:809`). Upstream base Dockerfile
(`mingchen/docker-android-build-box`, tag 1.29.0, file `Dockerfile`): `FROM ubuntu:22.04 as ubuntu` (line 39)
and apt installs `python3-pip \` (line 138). Upstream README @1.29.0 line 47 lists "Python 3.8.10"
(README text; may be stale for ubuntu 22.04). Exact version: not found in either repo.

**JDKs installed (found, upstream Dockerfile @1.29.0)**: lines 123-126 `openjdk-8-jdk`, `openjdk-11-jdk`,
`openjdk-17-jdk`, `openjdk-21-jdk`; jenv registers all four (lines 209-212) and sets `jenv global 21` (214).
`JENV_ROOT="/opt/jenv"` (line 61); PATH starts with `/opt/jenv/shims:/opt/jenv/bin` (ghcr config Env), so
`java` resolves through jenv shims. No `JAVA_HOME` ENV in the published image config.

**JDK selection (found)**: the harness overwrites the jenv global file: `> /opt/jenv/version` (`tusky.py:96`).
`detect_jdk.sh` (`tusky.py:37-77`): checks out `$BASE_SHA` (45), greps `jvmTarget`/`jvmToolchain` in
`build.gradle(.kts)` (51), then `jvmTarget`/`jdk` in `gradle/libs.versions.toml` (55), default
`REQUIRED_JDK=17` (63), accepts only `8|11|17|21)` (68) else `echo "17"` (72), then `git reset --hard HEAD` (77).
AntennaPod's variant (`antennapod.py:53-77`) reads `sourceCompatibility JavaVersion.VERSION_` from
`common.gradle` and `agpVersion` from `build.gradle`; AGP major >= 8 -> 17, >= 7 -> 11.

## 3. Gradle: pre-build, GRADLE_USER_HOME, user

**Pre-build at image build (found)**: `RUN bash /home/prepare.sh` (`tusky.py:340`) runs
`{test_cmd} --no-daemon --stacktrace --continue --parallel || true` (`tusky.py:188`) where
`test_cmd=self.pr.test_command or "./gradlew clean test --max-workers 8"` (`tusky.py:202`). The whole
unit-test suite executes at build, so the Gradle wrapper, dependencies and build outputs (including the
base run's `TEST-*.xml` under `*/build/test-results/`) are baked into the image. Default command without
`--max-workers 8`: Geto (`repos/kotlin/jackeblan/geto.py:202`) and AntennaPod (`antennapod.py:206`) use
`"./gradlew clean test"`. `pr.test_command` comes from the dataset (`mobiledev_bench/harness/pull_request.py:184`).

**GRADLE_USER_HOME (found: not set)**: no `ENV GRADLE_USER_HOME` in any generated Dockerfile, none in the
upstream Dockerfile (grep), none in the published image's Env (ghcr config). Gradle's default
`$HOME/.gradle` applies; with `User: root` that is `/root/.gradle`. Exceptions: the proxy branch appends
`echo 'export GRADLE_USER_HOME=/root/.gradle' >> ~/.bashrc` (`tusky.py:369`, only with `--global_env`
proxy vars; `.bashrc` is not sourced by `bash script.sh`); Thunderbird scripts `export GRADLE_USER_HOME=/tmp/.gradle`
(`repos/kotlin/thunderbird/thunderbirdandroid.py:188`) and write a `gradle.properties` with
`org.gradle.workers.max=4` and `-Xmx6g` (195-196); WordPress copies `/home/gradle.properties` with dummy
secrets into the repo (`wordpress_android.py:221-222`, properties at 120-148).

**Root (found)**: `USER root` (`tusky.py:103`); published config: `User: root`, `Cmd: ['/bin/bash']`, no ENTRYPOINT.

## 4. run.sh, test-run.sh, fix-run.sh and log parsing

All three are COPYed to `/home/` and invoked as `bash /home/run.sh` (`tusky.py:414`), `bash /home/test-run.sh`
(420), `bash /home/fix-run.sh` (426). None runs `git checkout`/`reset`; they assume the build-time state.

**run.sh (found, `tusky.py:207-228`)**: `set -e`; `cd /home/{pr.repo}`; `chmod +x gradlew`;
`{test_cmd} --no-daemon --stacktrace --continue --parallel || true` (214); then collect (below).

**test-run.sh (found, `tusky.py:233-271`)**: patch strategy chain
`git apply --verbose /home/test.patch` (240) -> `git apply --verbose --ignore-space-change --ignore-whitespace`
(242) -> `patch --batch --fuzz=3 -p1 < /home/test.patch` (244) -> else `exit 1` (248); `chmod +x gradlew`;
`./gradlew clean --no-daemon || true` (254); test command (257); collect.

**fix-run.sh (found, `tusky.py:276-327`)**: same three-step chain for `/home/test.patch` (283-292), then for
`/home/fix.patch` (`git apply --verbose /home/fix.patch`, 296; whitespace variant 298; `patch --batch --fuzz=3 -p1` 300);
`./gradlew clean --no-daemon || true` (310); test command (313); collect.

**Collection (found, `tusky.py:217-227`)**: `find . -name "TEST-*.xml" -type f 2>/dev/null | head -30` and each
file is printed between `=== XML FILE: $file ===` and `=== END XML FILE ===`; then
`find . -path "*/test-results/*" -name "*.xml" -type f ... | head -30` between `=== TEST RESULT: $file ===` /
`=== END TEST RESULT ===`. Only the first 30 files of each find are captured; results beyond that are lost.

**Parsing (found, `tusky.py:428-470`)**: sections via regex `=== XML(?:\s+FILE)?:\s*(.+?)\s*===\s*\n(.*?)\n=== END` (435)
and `=== TEST RESULT:` (436); testcases via
`<testcase[^>]*name="([^"]+)"[^>]*classname="([^"]+)"[^>]*(?:/>|>(.*?)</testcase>)` (440) — note `name=` must
precede `classname=` in the tag; `full_test_name = f"{class_name}.{test_name}"` (449); `<failure`/`<error` ->
failed (453), `<skipped` -> skipped (455), otherwise passed; self-closing tag -> passed (461). Geto adds a
console fallback `^(.+)\s+>\s+(.+)\s+(PASSED|FAILED|SKIPPED)$` (`geto.py:473`).

**f2p/p2p derivation (found, `mobiledev_bench/harness/report.py:130-138`)**: per test name,
`Test(run, test, fix)` from the three stages (`report.py:64-68`, missing -> `TestStatus.NONE`);
`p2p` = `test.test == TestStatus.PASS and test.fix == TestStatus.PASS` (131-132);
`f2p` = `test.test == TestStatus.FAIL and test.fix == TestStatus.PASS` (133-134); `s2p` SKIP->PASS (135);
`n2p` NONE->PASS (137). Validity: `fix_patch_result.all_count == 0` -> invalid (95); any PASS->FAIL -> invalid
(102); nothing transitioned to PASS -> invalid (110-116). At evaluation only the fix stage is executed
(`run_evaluation.py:805-816`); the run/test baselines come from the dataset:
`run_log=self.dataset[task.id].run_result` (`mobiledev_bench/harness/gen_report.py:503-504`), hence
`data/dataset_with_baselines.jsonl` is required (`mobiledev_bench/harness/README.md:110`). A report is valid
only if every dataset `p2p`/`f2p` name reappears (`gen_report.py:464-476`). Log files: `run.log`,
`test-patch-run.log`, `fix-patch-run.log` (`mobiledev_bench/harness/constant.py:25-27`), under
`<workdir>/<org>/<repo>/evals/pr-N/` (`run_evaluation.py:719-725`; `ReportTask.fix_patch_run_log`, `report.py:233-241`).

## 5. Image naming on GHCR

**Local name (found)**: prefix `return "mobiledevbench"` (`image.py:96`);
`f"{self.image_prefix()}/{self.pr.org}_mb_{self.pr.repo}".lower()` (`image.py:100`); tag `f"pr-{self.pr.number}"`
(`tusky.py:136`) or `"base"` (`tusky.py:27`). Example: `mobiledevbench/tuskyapp_mb_tusky:pr-2713`.

**GHCR reference used by the Python harness (found)**: `ghcr_image = f"ghcr.io/{ghcr_username}/{repo_name}:{tag}"`
(`mobiledev_bench/utils/docker_util.py:51`) with `repo_name` = the local name minus tag, i.e.
`ghcr.io/mobiledev-bench/mobiledevbench/{org}_mb_{repo}:pr-{N}`; `--ghcr_username` defaults to
`"mobiledev-bench"` (`run_evaluation.py:207`). After pulling it is re-tagged to the local name (`docker_util.py:71`).

Two concrete references (from `scripts/images.txt` line 261 `tuskyapp_mb_tusky:pr-2713` and line 1
`antennapod_mb_antennapod:pr-6573`):
- `ghcr.io/mobiledev-bench/mobiledevbench/tuskyapp_mb_tusky:pr-2713`
- `ghcr.io/mobiledev-bench/mobiledevbench/antennapod_mb_antennapod:pr-6573`

**Discrepancy (found)**: `scripts/images.txt` (407 lines, all matching `{org}_mb_{repo}:pr-{N}`) carries no
`mobiledevbench/` prefix, although `scripts/pull_images_from_ghcr.sh:5` says images are
`mobiledevbench/{org}_mb_{repo}:pr-{number}`. The script builds `ghcr.io/${GHCR_USERNAME}/${repo_name}:${tag}`
(line 49), which from the file yields `ghcr.io/mobiledev-bench/tuskyapp_mb_tusky:pr-2713`. Registry check
(anonymous ghcr.io v2 API, 2026-10-28): `.../mobiledev-bench/mobiledevbench/tuskyapp_mb_tusky/tags/list` returns
20 tags `["base","pr-2344","pr-2713",...]`; `.../mobiledev-bench/tuskyapp_mb_tusky` returns no pull token
(`DENIED`). Use the form with `mobiledevbench/` in the path. GHCR also carries pr- tags absent from
images.txt (e.g. tusky `pr-2344`, `pr-2755`).

**Per-repo base image published (found via registry)**: tag `base` exists for `tuskyapp_mb_tusky`,
`antennapod_mb_antennapod` and `thunderbird_mb_thunderbird-android`; it is not listed in `images.txt`
(no `:base` line) and the harness only pulls `pr-N` images (`run_evaluation.py:740-743`).

## 6. Platform and size

**Platform (found)**: the repo's build call passes no platform (`docker_util.py:124-132`); the inference config
states `docker_platform: linux/amd64    # matches mobiledev-bench's instance images, not the host`
(`mobiledev_bench/inference/backends/mini_swe_agent.yaml:18`; `config.py:53`). Registry: the `pr-2713` manifest
is a single-arch `application/vnd.docker.distribution.manifest.v2+json` with config `architecture: amd64, os: linux`.
The upstream base supports arm64 too (`# support amd64 and arm64`, upstream Dockerfile line 88) but the
published instance images are amd64 only.

**Size**: not found in any mobiledev-bench script or README. Registry manifests: `tuskyapp_mb_tusky:pr-2713`
48 layers, 5,096,721,097 compressed bytes (~4.75 GiB); `tuskyapp_mb_tusky:base` 40 layers ~3.80 GiB compressed.
Uncompressed size: not found. Upstream README @1.29.0 line 99 mentions "the image needs 16.2GB" for its
own `1.25.0` raw image.

## 7. Other facts for an overlay author

- Gold patches are baked into the image: `File(".", "fix.patch", f"{self.pr.fix_patch}")` and `test.patch`
  (`tusky.py:143-152`) are COPYed to `/home/fix.patch` and `/home/test.patch`. Nothing in the harness or the
  inference runner deletes them. An overlay must not leak `/home/fix.patch` to the agent.
- Run-time mounts (found): the model patch is bind-mounted over `/home/fix.patch` with `"mode": "rw"`
  (`run_evaluation.py:752-757`; target from `return "/home/fix.patch"`, `image.py:115`). When
  `"gpt-5.2" in patch.model` and the patch starts with `*** Begin Patch` (747-750), `apply_begin_patch.py` is
  mounted read-only at `/home/apply_begin_patch.py` (760-763) and the command becomes
  `bash -c 'python3 /home/apply_begin_patch.py /home/fix.patch /home/{repo} && bash /home/fix-run.sh'` (807-811).
- Command (found): `bash /home/fix-run.sh` unless `--fix_patch_run_cmd` is given (`run_evaluation.py:162-167`, 805).
- Environment (found): `environment=global_env` (`docker_util.py:216`) from `--global_env` (default None,
  `run_evaluation.py:120-125`); nothing is set by default. Image Env (ghcr config): `PATH=/opt/jenv/shims:...`,
  `ANDROID_HOME=/opt/android-sdk`, `ANDROID_NDK=/opt/android-sdk/ndk/latest`, `FLUTTER_HOME=/opt/flutter`,
  `JENV_ROOT=/opt/jenv`, `TZ=Etc/UTC`, `LANG/LANGUAGE/LC_ALL=en_US.UTF-8`, `NODE_ENV=production`,
  `DEBIAN_FRONTEND=noninteractive`.
- Container flags (found): `remove=False, detach=True` (`docker_util.py:211-212`), no `--platform`, no CPU/memory
  limits, no network restriction in evaluation (the inference side uses an internal network plus a Squid egress
  proxy, `runner.py:155-177`). Containers are force-removed in `finally` (`docker_util.py:264`).
- Timeouts (found): Docker client `docker.from_env(timeout=600)` (`docker_util.py:23`); `timeout: int = 3600`
  (`docker_util.py:205`) applies only to `container.wait(timeout=timeout)` in the no-`output_path` branch (243);
  evaluation always passes `output_path` (`run_evaluation.py:774`), so logs stream with `follow=True`
  (`docker_util.py:225`) and no wall-clock limit is enforced. Gradle flags: `--no-daemon --stacktrace --continue --parallel`
  on every test run; `--max-workers 8` in the default command of most Kotlin repos (`tusky.py:202`).
- Parallelism (found): `--max_workers_run_instance` default 8 (`run_evaluation.py:154-160`, README.md:89);
  `run_evaluation.sh:28` sets `MAX_WORKERS_RUN_INSTANCE="${MAX_WORKERS_RUN_INSTANCE:-1}"  # Set to 1 to avoid parallel runs`;
  `--max_workers_build_image` default 8 (148-152).
- Remote image lifecycle (found): with `--use_remote_images` the image is pulled before each instance (740-745)
  and deleted afterwards (`docker_util.delete`, 819-821); an overlay `FROM` these images must pull them itself.
- Resume (found): an existing `report.json` skips the instance (`run_evaluation.py:732-737`); an empty
  `fix_patch` is skipped before any pull (713-717).
- Stale results: because `prepare.sh` ran the base suite at build, `*/build/test-results/*.xml` from that run
  exist in the image; the shipped scripts always `clean` first (`tusky.py:254,310` and `clean test` in the
  default command). An overlay grader that skips `clean` would parse those stale files.
- Upstream base facts (found, upstream Dockerfile @1.29.0): `ARG NDK_VERSION="28.0.13004108"` (16),
  `ARG FLUTTER_VERSION="3.24.5"` (25), `ARG JENV_RELEASE="0.5.6"` (28), upstream default WORKDIR `/project` (488)
  is overridden to `/home` by the harness.
